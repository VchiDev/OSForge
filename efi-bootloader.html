UEFI & BIOS Bootloader Lab

Learn how computers start operating systems. Build a UEFI application, assemble a BIOS boot sector, and test both in a virtual machine.

Overview Setup UEFI Lab UEFI Testing BIOS Lab UEFI: Read Files UEFI: Graphics UEFI: Memory Map BIOS: Disk Loading BIOS: Stage 2 BIOS: Protected Mode Troubleshooting Resources

What you'll build

UEFI application

Compile a 64-bit EFI application named BOOTX64.EFI using GCC and GNU-EFI.

UEFI virtual machine

Place the application on a FAT disk image and run it using QEMU and OVMF firmware.

Legacy BIOS boot sector

Write a 16-bit assembly boot sector, assemble it with NASM, and test it with QEMU.

Important distinction: A UEFI application and a BIOS boot sector are different executable formats. UEFI firmware loads EFI applications from a supported filesystem; legacy BIOS loads a boot sector from a boot device. The two labs use separate workflows.

These labs are educational starting points. A working bootloader does not automatically provide a complete operating system, memory manager, process scheduler, device drivers, or graphical interface.

1. Set up your development environment

These instructions target Ubuntu, Debian, or Ubuntu running through Windows Subsystem for Linux (WSL). The package names and firmware paths can vary by distribution.

Install the development tools

sudo apt update
sudo apt install build-essential binutils gcc make gnu-efi nasm qemu-system-x86 ovmf dosfstools mtools python3

The main tools are:

Using Visual Studio Code

  1. Install Visual Studio Code on Windows or Linux.
  2. For WSL, install Microsoft's WSL extension.
  3. Open your project directory in the WSL environment.
  4. Run build commands in the Ubuntu/WSL terminal, not a separate Windows terminal.

Keep the source files in the same environment where the compiler and build tools are installed. For this tutorial, the working directory will be ~/osforge-bootlab.

2. UEFI lab: build an EFI application

UEFI applications are commonly stored as PE/COFF files. On x86-64 systems, the standard removable-media boot path is EFI/BOOT/BOOTX64.EFI.

Create the project directory

mkdir -p ~/osforge-bootlab/uefi
cd ~/osforge-bootlab/uefi

Create main.c

This minimal application prints a message and waits for a key. It uses GNU-EFI's UEFI interfaces. 

#include <efi.h>
#include <efilib.h>

EFI_STATUS EFIAPI efi_main(
    EFI_HANDLE ImageHandle,
    EFI_SYSTEM_TABLE *SystemTable
) {
    InitializeLib(ImageHandle, SystemTable);

    Print(L"Welcome to OSForge UEFI Boot Lab!\r\n");
    Print(L"UEFI application started successfully.\r\n");
    Print(L"Press any key to exit.\r\n");

    uefi_call_wrapper(
        SystemTable->ConIn->Reset, 2,
        SystemTable->ConIn, FALSE
    );

    uefi_call_wrapper(
        SystemTable->ConIn->ReadKeyStroke, 2,
        SystemTable->ConIn, &(EFI_INPUT_KEY){0}
    );

    return EFI_SUCCESS;
}

Create the Makefile

GNU-EFI file locations differ between distributions. The following Makefile assumes common Debian or Ubuntu package paths. 

ARCH = x86_64
EFI_INC = /usr/include/efi
EFI_ARCH_INC = /usr/include/efi/$(ARCH)
EFI_LIB = /usr/lib

CC = gcc
LD = ld
OBJCOPY = objcopy

CFLAGS = -I$(EFI_INC) -I$(EFI_ARCH_INC) \
         -fpic -ffreestanding -fno-stack-protector \
         -fno-stack-check -fshort-wchar -mno-red-zone \
         -maccumulate-outgoing-args

LDFLAGS = -nostdlib -znocombreloc -T \
          /usr/lib/elf_x86_64_efi.lds \
          -shared -Bsymbolic

all: BOOTX64.EFI

main.o: main.c
	$(CC) $(CFLAGS) -c main.c -o main.o

boot.so: main.o
	$(LD) $(LDFLAGS) \
	    /usr/lib/crt0-efi-x86_64.o main.o \
	    -L$(EFI_LIB) -lefi -lgnuefi -o boot.so

BOOTX64.EFI: boot.so
	$(OBJCOPY) --target=efi-app-x86_64 \
	    boot.so BOOTX64.EFI

clean:
	rm -f main.o boot.so BOOTX64.EFI

.PHONY: all clean
Makefile note: Recipe lines must begin with a real tab. GNU-EFI paths and objcopy target names can vary by toolchain; if the build fails, follow the troubleshooting section.

Compile the application

make
file BOOTX64.EFI

The output should be a PE/COFF EFI application. If compilation fails, confirm that GNU-EFI and the required development tools are installed.

3. Test the UEFI application in QEMU

UEFI firmware needs a FAT-formatted EFI System Partition containing the executable at the standard removable-media path.

Create the disk image

cd ~/osforge-bootlab/uefi
mkdir -p esp/EFI/BOOT
cp BOOTX64.EFI esp/EFI/BOOT/BOOTX64.EFI
dd if=/dev/zero of=uefi.img bs=1M count=64
mkfs.vfat uefi.img
mcopy -i uefi.img -s esp/EFI ::

If your version of mtools does not accept the copy command above, create the directories inside the image and copy the EFI file with individual mmd and mcopy commands.

Locate OVMF firmware

find /usr/share -iname '*OVMF*CODE*.fd' 2>/dev/null

On many Debian-based distributions, the firmware file is located under /usr/share/OVMF/. Use the path returned by your system.

Boot the virtual machine

Replace the firmware path below with the OVMF code image found on your system. 

qemu-system-x86_64 \
  -machine q35 \
  -m 512M \
  -bios /usr/share/OVMF/OVMF_CODE.fd \
  -drive format=raw,file=uefi.img
Checkpoint: If the firmware detects the disk and launches your EFI application, the UEFI lab is working. If the application is not found, check the disk image's directory structure and the firmware path.

What you have learned

  • UEFI firmware can load a PE/COFF EFI application.
  • A FAT filesystem can contain the standard removable-media boot path.
  • QEMU and OVMF let you test boot code without changing your physical computer's firmware settings.

4. Legacy BIOS lab: build a boot sector

Traditional x86 BIOS firmware loads a boot sector from a boot device. A classic boot sector is 512 bytes long and ends with the signature 55 AA (stored as 0xAA55 in little-endian assembly notation).

Create the project directory

mkdir -p ~/osforge-bootlab/bios
cd ~/osforge-bootlab/bios

Create boot.asm

bits 16
org 0x7C00

start:
    cli
    xor ax, ax
    mov ds, ax
    mov es, ax
    mov ss, ax
    mov sp, 0x7C00
    sti

    mov si, message

.print:
    lodsb
    test al, al
    jz .halt

    mov ah, 0x0E
    int 0x10
    jmp .print

.halt:
    cli

.loop:
    hlt
    jmp .loop

message db 'Welcome to OSForge BIOS Boot Lab!', 0

times 510-($-$$) db 0
dw 0xAA55

Assemble the boot sector

nasm -f bin boot.asm -o boot.bin
wc -c boot.bin

The output must be exactly 512 bytes. If it is not, check the padding directive and ensure that the source fits within the first 510 bytes before the signature.

Test it in QEMU

qemu-system-i386 -drive format=raw,file=boot.bin
Checkpoint: The virtual machine should display the welcome message and then halt. This is a tiny boot sector, not yet a complete bootloader capable of loading a kernel.

Understand the BIOS boot process

  1. Firmware initializes enough hardware to begin booting.
  2. Firmware selects a boot device and loads its boot sector.
  3. The boot sector runs in the processor's initial 16-bit environment.
  4. A more capable bootloader can load additional code from disk.
  5. The loader eventually transfers control to the operating system kernel.

UEFI lesson 2: Reading files

UEFI provides file-system protocols that allow an EFI application to open files from a supported volume. A bootloader can use this capability to locate a kernel image, a configuration file, or other boot resources.

The file-loading workflow

  1. Use the loaded-image protocol to identify the device that launched the application.
  2. Locate the Simple File System Protocol for that device.
  3. Open the volume root using OpenVolume.
  4. Open the requested file with Open.
  5. Query the file size and allocate a suitably sized buffer.
  6. Read the file, check the returned status, and close all handles.

Important concepts

  • EFI_LOADED_IMAGE_PROTOCOL describes the loaded EFI image.
  • EFI_SIMPLE_FILE_SYSTEM_PROTOCOL provides access to a filesystem.
  • EFI_FILE_HANDLE represents an open file or directory.
  • EFI_STATUS reports whether an operation succeeded.
Safety check: Do not assume that a file exists or that its contents are valid just because it opened. Check file sizes, handle errors, and validate a kernel image before transferring control to it.

Checkpoint

Extend your UEFI application so it can open a text file on the EFI System Partition and report whether the file was found. Once that works, practice reading its contents into a buffer.

UEFI lesson 3: Graphics Output Protocol

The Graphics Output Protocol (GOP) gives an EFI application access to display-mode information and a framebuffer. It can be used to show a graphical boot screen before the kernel initializes its own graphics system.

What GOP provides

  • Current display resolution.
  • Available display modes.
  • Framebuffer base address and size.
  • Pixel format and pixels-per-scan-line information.

Locate the protocol

EFI_GRAPHICS_OUTPUT_PROTOCOL *Gop = NULL;

EFI_STATUS Status = uefi_call_wrapper(
    BS->LocateProtocol, 3,
    &GraphicsOutputProtocol,
    NULL,
    (VOID **)&Gop
);

if (EFI_ERROR(Status) || Gop == NULL) {
    Print(L"GOP is unavailable.\r\n");
    return EFI_UNSUPPORTED;
}

Print(L"Screen: %u x %u\r\n",
    Gop->Mode->Info->HorizontalResolution,
    Gop->Mode->Info->VerticalResolution
);

This example assumes the relevant GNU-EFI headers and boot-services aliases are available in your application. It is a snippet to integrate into your existing EFI entry point, not a standalone application.

Framebuffer precautions

  • Do not assume every pixel format uses the same channel ordering.
  • Use PixelsPerScanLine when calculating row offsets.
  • Respect the framebuffer size and avoid writing beyond its bounds.
  • After exiting boot services, the kernel must establish its own graphics and memory-management assumptions.

Checkpoint

Display the current resolution in your UEFI application. Next, investigate the available modes and plan a framebuffer drawing function that respects the mode's pixel format.

UEFI lesson 4: Memory map and boot-services handoff

Before transferring control to a kernel, a bootloader often needs the firmware memory map. UEFI's GetMemoryMap function reports descriptors that describe memory regions and their types.

Memory-map workflow

  1. Call GetMemoryMap to discover the required buffer size.
  2. Allocate a buffer large enough for the descriptors, allowing for growth.
  3. Call GetMemoryMap again and save the map key and descriptor size.
  4. Finish required allocations and avoid unrelated boot-service calls.
  5. Call ExitBootServices with the current map key.
  6. If the call returns EFI_INVALID_PARAMETER, refresh the map and retry according to the UEFI rules.
Important: ExitBootServices ends the normal boot-services phase. Once it succeeds, do not continue calling boot-service functions. A kernel handoff requires a valid entry point, a defined calling convention, a prepared stack, and a memory layout understood by the kernel.

Questions to answer before launching a kernel

  • Where will the kernel image be loaded in physical memory?
  • How will the bootloader communicate the memory map to the kernel?
  • Which memory regions may the kernel safely use?
  • Will the kernel continue using the firmware-provided framebuffer?
  • What CPU mode, paging state, stack, and entry convention will be active at handoff?

Checkpoint

Write down the memory-map information your future kernel will need. Define a boot-information structure before attempting the actual transfer of control.

BIOS lesson 2: Loading additional disk sectors

A 512-byte boot sector is too small for a sophisticated bootloader. A common next step is to use BIOS disk services to read additional sectors into memory and jump to the code that was loaded.

Learn the BIOS disk interface

Traditional BIOS provides interrupt INT 13h for disk operations. Older interfaces use cylinder-head-sector addressing; extensions provide logical block addressing (LBA).

  • The BIOS provides a boot-drive identifier in DL on entry.
  • The bootloader should preserve the drive identifier before other code changes it.
  • Disk reads can fail, so a loader needs an error path.
  • The destination buffer must be in an appropriate memory region.
  • The bootloader must know where the additional sectors are stored.

Design a disk-loading plan

  1. Reserve a known disk region for the second stage.
  2. Choose a disk-read method supported by the target BIOS.
  3. Choose a destination address and check that it does not overlap the boot sector or stack.
  4. Read the second stage and verify that the operation succeeded.
  5. Transfer control to its documented entry point.
Important: Disk geometry, sector numbering, BIOS extensions, and memory layout matter. Do not assume a disk read succeeded simply because the emulator did not show an error. Test the loading stage separately before adding kernel loading.

Checkpoint

Plan a disk image that contains the boot sector followed by a distinguishable second-stage payload. Confirm the payload location and size before implementing the disk-reading routine.

BIOS lesson 3: Two-stage bootloaders

A two-stage bootloader divides the initial boot process into a tiny first stage and a larger second stage. This makes it easier to develop and debug the disk-loading logic separately from the more complex work of loading a kernel.

Stage responsibilities

Stage 1

  • Initialize the basic CPU state.
  • Preserve the BIOS boot-drive identifier.
  • Read the known location of stage two.
  • Check the read result and transfer control.

Stage 2

  • Provide a more capable console.
  • Read more data from disk.
  • Optionally parse a supported filesystem.
  • Load and validate a kernel image.

Kernel handoff

  • Prepare a known stack and CPU state.
  • Define the kernel entry address.
  • Pass boot information in a documented structure.
  • Transfer control only when the kernel's prerequisites are met.

Debugging strategy

  1. Make stage one display a message.
  2. Make stage two display a different message.
  3. Verify the disk read and control transfer.
  4. Add one new feature at a time.
  5. Keep the kernel-loading logic separate until the earlier stages work.

Do not assume that registers, the stack, or segment values have the desired state just because the code worked in one emulator. Initialize and document the state your code depends on.

BIOS lesson 4: Preparing for protected mode

A 32-bit protected-mode kernel needs more than a jump instruction. The bootloader must prepare a Global Descriptor Table (GDT), manage interrupts during the transition, enable the protection-enable bit in CR0, and perform a far jump to reload CS.

Transition checklist

  1. Load a valid GDT with a null descriptor and suitable code and data descriptors.
  2. Disable maskable interrupts and ensure the boot code has a known stack.
  3. Set the protection-enable bit in CR0.
  4. Use a far jump to a 32-bit code selector and initialize the data segment registers.
  5. Set a known 32-bit stack and jump to the kernel entry point.
Advanced step: Do not blindly copy a mode-switch sequence. Descriptor values, assembler mode, memory addresses, and the kernel's entry convention must agree. Test the transition as a separate milestone in QEMU before combining it with disk loading.

Checkpoint

After the transition, display a marker through a carefully prepared video-memory or serial-output path. If the VM resets or hangs, simplify the transition and inspect it with QEMU's debugger.

5. Troubleshooting

make: No rule to make target 'clean'

You may be in the wrong directory, or your Makefile may not contain a clean: target. Run pwd and ls to check your current directory.

missing separator

Makefile recipe lines must begin with a real TAB, not spaces.

objcopy: file format not recognized

Check the input with file boot.so and inspect supported output formats with objcopy --info. EFI target names and options differ between versions of GNU Binutils. Use the target supported by your installed toolchain.

GNU-EFI startup object not found

Check whether GNU-EFI is installed with dpkg -L gnu-efi. If the required files are installed elsewhere, adjust the Makefile paths for your distribution.

libefi.a or libgnuefi.a is missing

Use dpkg -L gnu-efi to locate the libraries and confirm that both are present. Some distributions place architecture-specific libraries in a separate directory.

EFI headers are missing

Check for /usr/include/efi/efi.h and /usr/include/efi/x86_64/. Adjust the include paths if your distribution installs headers elsewhere.

BOOTX64.EFI builds but does not boot

  • Confirm the disk contains EFI/BOOT/BOOTX64.EFI.
  • Use x86-64 UEFI firmware for an x86-64 application.
  • Check that the OVMF code and variables images are compatible.
  • Confirm that firmware is booting the intended disk image.
  • Rebuild after changing source files and copy the new executable to the disk image.

QEMU cannot open a graphical window

Run QEMU from a Linux desktop session or a WSL environment with working graphical support. Check that the QEMU emulator package is installed and your display environment is available.

BIOS boot sector is not 512 bytes

Ensure the source pads through byte 510 and includes dw 0xAA55. Reassemble and verify with wc -c boot.bin.
