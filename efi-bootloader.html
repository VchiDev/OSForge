OSFORGE HANDS-ON LAB

Build your own bootloader

Learn how to create boot software for your own operating system. This workshop covers UEFI applications, legacy BIOS boot sectors, Linux development environments, VS Code, and virtual machine testing.

Safety first: Build and test in an emulator using disposable virtual disks. Do not install experimental bootloaders onto your everyday computer's EFI System Partition or physical disk.

Choose your boot method

UEFI / EFI

Modern firmware loads a PE/COFF EFI application. Your application can locate a kernel, read configuration, and prepare the handoff to your OS.

Tools: GNU-EFI, GCC, binutils, QEMU, OVMF.

Start UEFI lab →

Legacy BIOS

BIOS begins by loading boot code into memory. Learn how a 512-byte boot sector executes and prints a message.

Tools: NASM, QEMU, VS Code.

Start BIOS lab →

Part 1 — Prepare your development environment

Option A: Ubuntu or Debian

Open a terminal on Ubuntu or Debian. Update the package index and install the development tools: 

sudo apt update
sudo apt install build-essential binutils nasm git make \
  qemu-system-x86 ovmf gnu-efi mtools dosfstools xorriso

The packages provide a compiler, linker, assembler, UEFI development files, and tools for building and testing boot images. Package availability and library locations vary by distribution version.

Option B: Windows with WSL

Open Windows PowerShell and install Ubuntu:

wsl --install Ubuntu

Restart Windows if requested. Open Ubuntu and create your Linux username and password. Then run the Ubuntu installation commands shown above inside the Ubuntu terminal.

Debian can also be installed through WSL. Use the same Debian package commands from its terminal.

Install VS Code

  1. Install Visual Studio Code on Windows or Linux.
  2. If using WSL, install the Microsoft Remote - WSL extension.
  3. Open your Ubuntu or Debian terminal.
  4. Create a project folder and open it using code ..
  5. Create and edit your source files in VS Code.
  6. Run compilation and emulator commands in the integrated terminal.

Official setup guide: VS Code with WSL .

Create the project folder

Run these commands inside Ubuntu or Debian:

mkdir -p ~/osforge-bootlab/uefi
mkdir -p ~/osforge-bootlab/bios
cd ~/osforge-bootlab
code .

Your project will eventually look like this:

osforge-bootlab/
├── uefi/
│   ├── main.c
│   └── Makefile
└── bios/
    └── boot.asm
WSL note: Keep source files inside the Linux home directory, such as ~/osforge-bootlab, for a convenient Linux build workflow. QEMU can run Linux-side builds, but graphical emulator support depends on your WSL setup. If necessary, run QEMU natively on Windows or use a Linux virtual machine.
TRACK A

Part 2 — Create a UEFI application

In this lab, you will create a real EFI application that displays a message. It is the first step toward a custom bootloader that loads a kernel.

Step 1 — Understand the files

  • main.c: your EFI application's entry point.
  • Makefile: commands for compiling and linking it.
  • BOOTX64.EFI: the final x86-64 EFI application.
  • boot.so: an intermediate linked image used by the build.

Step 2 — Write main.c

In the uefi directory, create main.c: 

#include <efi.h>
#include <efilib.h>

EFI_STATUS EFIAPI efi_main(
    EFI_HANDLE image_handle,
    EFI_SYSTEM_TABLE *system_table
) {
    InitializeLib(image_handle, system_table);

    Print(L"OSForge UEFI Bootloader Lab\r\n");
    Print(L"UEFI application started successfully.\r\n");
    Print(L"Next step: load a kernel image.\r\n");

    return EFI_SUCCESS;
}

This example uses the GNU-EFI headers and library. It is not a normal Linux executable: the UEFI firmware provides the environment in which the application starts.

Step 3 — Locate GNU-EFI build files

The exact paths depend on your Ubuntu or Debian release and architecture. Find the installed files: 

dpkg -L gnu-efi | grep -E \
'crt0-efi-x86_64.o|elf_x86_64_efi.lds|libefi.a|libgnuefi.a'

You need the x86-64 startup object, linker script, and both GNU-EFI libraries. If any are missing, check the package installation and ensure you are using an x86-64 development environment.

Step 4 — Create the Makefile

Create uefi/Makefile. Use the following as a starting point, replacing the example paths with the locations found in Step 3. 

ARCH = x86_64

EFI_INC = /usr/include/efi
EFI_ARCH_INC = /usr/include/efi/x86_64

EFI_LIBDIR = /usr/lib
EFI_LDS = $(EFI_LIBDIR)/elf_x86_64_efi.lds
EFI_CRT = $(EFI_LIBDIR)/crt0-efi-x86_64.o

CC = gcc
LD = ld
OBJCOPY = objcopy

CFLAGS = -I$(EFI_INC) -I$(EFI_ARCH_INC) \
  -fpic -ffreestanding -fno-stack-protector \
  -fno-stack-check -fshort-wchar -mno-red-zone \
  -maccumulate-outgoing-args

all: BOOTX64.EFI

main.o: main.c
	$(CC) $(CFLAGS) -c main.c -o main.o

boot.so: main.o
	$(LD) -nostdlib -znocombreloc \
	  -T $(EFI_LDS) -shared -Bsymbolic \
	  $(EFI_CRT) main.o -L$(EFI_LIBDIR) \
	  -lefi -lgnuefi -o boot.so

BOOTX64.EFI: boot.so
	$(OBJCOPY) \
	  -j .text -j .sdata -j .data -j .dynamic \
	  -j .dynsym -j .rel -j .rela -j .reloc \
	  --target=efi-app-x86_64 boot.so BOOTX64.EFI

clean:
	rm -f main.o boot.so BOOTX64.EFI

.PHONY: all clean
Important build detail: GNU-EFI library paths are not identical on every distribution. Some installations put the libraries under an architecture-specific subdirectory. Adjust EFI_LIBDIR and EFI_LDS to match your installed files. The Makefile is for x86-64 UEFI, not ARM64.

Step 5 — Compile the EFI application

From the UEFI project directory, run:

make clean
make

If the build succeeds, the directory should contain BOOTX64.EFI. If linking fails, recheck the library paths and ensure the GNU-EFI package matches the target architecture.

Verify the resulting file: 

file BOOTX64.EFI

Step 6 — Prepare a disposable EFI System Partition

UEFI firmware typically loads the default removable-media boot application for x86-64 from EFI/BOOT/BOOTX64.EFI on a FAT filesystem.

The following commands create a small, disposable FAT image. Run them inside the UEFI project directory: 

mkdir -p esp/EFI/BOOT
cp BOOTX64.EFI esp/EFI/BOOT/BOOTX64.EFI

dd if=/dev/zero of=uefi.img bs=1M count=64
mkfs.fat -F 32 uefi.img

mcopy -i uefi.img -s esp/EFI ::/

The image is a test disk, not your computer's real EFI partition. Do not substitute a physical disk device for uefi.img.

Step 7 — Boot with QEMU and OVMF

Locate the installed OVMF firmware files:

find /usr/share/OVMF /usr/share/ovmf \
  -type f 2>/dev/null

Identify a compatible x86-64 OVMF code image and, if available, its matching writable variable-store template. File names differ between distributions.

Launch QEMU using the paths for your installation:

qemu-system-x86_64 \
  -machine q35 \
  -m 512 \
  -drive if=pflash,format=raw,readonly=on,file=/PATH/TO/OVMF_CODE.fd \
  -drive format=raw,file=uefi.img

Replace /PATH/TO/OVMF_CODE.fd with the actual firmware path. Some setups also need a writable OVMF variable-store image. Follow the installed OVMF package's guidance if the firmware requires one.

If the application starts, you should see the OSForge messages in the virtual machine. If not, check that the EFI file is in the correct directory, the firmware architecture matches, and the image contains a readable FAT filesystem.

Step 8 — Turn the application into a bootloader

Printing a message is only the first milestone. A real kernel-loading bootloader must also:

  1. Find the kernel file and validate its format.
  2. Read the kernel image into suitable memory.
  3. Prepare a documented boot-information structure.
  4. Collect required firmware information, including the memory map.
  5. Handle UEFI boot-service shutdown correctly before transferring control.
  6. Jump to the kernel using the agreed entry point and calling convention.

Kernel loading is architecture- and executable-format-specific. Do not jump to an arbitrary file address and assume it is executable.

Official reference: UEFI specifications.

Part 3 — Create a BIOS boot sector

Legacy BIOS uses a different startup process from UEFI. For this beginner lab, you will write a 16-bit x86 boot sector with NASM. It prints a message using BIOS video services and then stops.

Step 1 — Create boot.asm

Open the bios directory in VS Code and create boot.asm: 

bits 16
org 0x7C00

start:
    xor ax, ax
    mov ds, ax
    mov es, ax
    mov ss, ax
    mov sp, 0x7C00

    mov si, message

print_character:
    lodsb
    test al, al
    jz finished

    mov ah, 0x0E
    int 0x10
    jmp print_character

finished:
    cli
halt:
    hlt
    jmp halt

message db 'OSForge BIOS Bootloader!', 13, 10
        db 'The boot sector is running.', 0

times 510 - ($ - $$) db 0
dw 0xAA55

This program assumes the traditional BIOS boot-sector environment. The signature 0xAA55 occupies the final two bytes in little-endian form. The sector is padded to 512 bytes.

Step 2 — Assemble the boot sector

Run these commands inside the BIOS project directory:

nasm -f bin boot.asm -o boot.bin
file boot.bin
wc -c boot.bin

The final command should report 512 bytes. If NASM reports an error, check the source file and make sure you installed NASM.

Step 3 — Test with QEMU

Run the boot sector as a virtual floppy image:

qemu-system-i386 \
  -drive file=boot.bin,format=raw,if=floppy

A QEMU window should display the OSForge BIOS message. The CPU then halts in a loop, leaving the message on screen.

Step 4 — Understand the limitations

This is a real boot sector, but it is not yet a full kernel loader. It depends on BIOS services, runs in 16-bit real mode, and does not load a separate kernel.

The next stages are:

  1. Read additional disk sectors using appropriate BIOS disk services.
  2. Load a second-stage bootloader into memory.
  3. Collect hardware and memory information.
  4. Prepare a protected-mode or long-mode transition as required.
  5. Load and enter a kernel using a defined memory layout and interface.
The BIOS disk, CPU-mode, and memory-transition stages are more advanced than printing a message. Build and verify each stage separately before trying to start a 32-bit or 64-bit kernel.

Alternative: Use GRUB for a kernel project

If your main goal is to develop a kernel rather than implement every bootloader stage, consider using GRUB with a documented Multiboot protocol. GRUB can handle much of the low-level boot process while you focus on kernel development.

Learn more: Official GNU GRUB manual .

Part 4 — QEMU versus VirtualBox

QEMU

Best for quick iteration from the terminal, repeatable boot commands, serial logs, and debugger integration.

UEFI testing uses OVMF; legacy BIOS testing uses the emulator's BIOS firmware.

QEMU documentation →

VirtualBox

Useful for testing a disk image through a graphical virtual machine interface.

Create a new disposable VM, choose the intended architecture, attach the boot image using the appropriate virtual storage configuration, and select EFI firmware when testing UEFI.

VirtualBox manual →

For a raw BIOS boot-sector image, QEMU is usually the simpler first test. VirtualBox workflows can require a disk image with the expected virtual drive layout. For UEFI, the image must include the appropriate EFI executable and filesystem layout.

Part 5 — Troubleshooting

QEMU says the boot image cannot be found

Check the current directory and confirm that the output file exists. Use an absolute path if necessary.

UEFI firmware does not launch the application

Check the EFI architecture, PE/COFF output, FAT image, and EFI/BOOT/BOOTX64.EFI path. Review the OVMF firmware configuration and any Secure Boot restrictions.

GNU-EFI linking fails

Confirm that the GNU-EFI headers, startup object, linker script, and libraries are installed. Update the Makefile paths to match the files on your distribution.

BIOS boot sector does not print

Verify the 512-byte output size and final boot signature. Ensure QEMU is using the image as a floppy and that the source uses 16-bit instructions with the expected load address.
