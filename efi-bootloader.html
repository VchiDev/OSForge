OSFORGE DEVELOPMENT LAB

UEFI & BIOS Bootloader Lab

Learn how to build and test a UEFI application and a legacy BIOS boot sector using Ubuntu, Debian, WSL, Visual Studio Code, and QEMU.

UEFI tutorial BIOS tutorial Troubleshooting
What you'll build: a UEFI application named BOOTX64.EFI and a 512-byte BIOS boot sector named boot.bin. These introductory examples do not yet load a separate OS kernel.

1. Set up your development environment

Use Ubuntu, Debian, or Ubuntu running under Windows Subsystem for Linux (WSL).

Install the tools

sudo apt update
sudo apt install build-essential binutils nasm git make 
  qemu-system-x86 ovmf gnu-efi mtools dosfstools python3

Using WSL on Windows

In Windows PowerShell, install Ubuntu if necessary:

wsl --install Ubuntu

Restart if requested, launch Ubuntu, and finish its initial setup. Install Visual Studio Code on Windows and add Microsoft's WSL extension. From the Ubuntu terminal, open your current Linux directory with:

code .
Run Linux commands in the Ubuntu/Debian terminal, not directly in PowerShell. Keep this project inside your Linux home directory.

2. UEFI bootloader tutorial

UEFI applications run under UEFI firmware. On x86-64 removable-media boot, the standard fallback path is EFI/BOOT/BOOTX64.EFI on a supported FAT filesystem.

Step 1 — Create the project directory

mkdir -p ~/osforge-bootlab/uefi
cd ~/osforge-bootlab/uefi
pwd

The displayed path should end in osforge-bootlab/uefi. Create both files in this directory.

Step 2 — Create main.c

Copy and run the entire block, including the final EOF line:

cat > main.c <<'EOF'
#include <efi.h>
#include <efilib.h>

EFI_STATUS EFIAPI efi_main(
    EFI_HANDLE image_handle,
    EFI_SYSTEM_TABLE *system_table
) {
    InitializeLib(image_handle, system_table);

    Print(L"OSForge UEFI Bootloader Lab\r\n");
    Print(L"UEFI application started successfully.\r\n");
    Print(L"Next step: load a kernel image.\r\n");

    return EFI_SUCCESS;
}
EOF

Verify the source file:

ls -l main.c

Step 3 — Check GNU-EFI

dpkg -L gnu-efi | grep -E \
'crt0-efi-x86_64.o|elf_x86_64_efi.lds|libefi.a|libgnuefi.a'

If the files are not listed, try:

sudo apt update
sudo apt install --reinstall gnu-efi

Step 4 — Generate the Makefile safely

Important fix: GNU Make requires a real TAB at the beginning of each recipe line. If an editor changes tabs to spaces, the build fails with missing separator. Instead of typing or pasting a Makefile with fragile indentation, use Python to generate it correctly.

Make sure you are still in ~/osforge-bootlab/uefi. Run this entire command block in the Ubuntu terminal:

cd ~/osforge-bootlab/uefi

python3 - <<'PY'
from pathlib import Path

content = """CC = gcc
LD = ld
OBJCOPY = objcopy

EFI_INC = /usr/include/efi
EFI_ARCH_INC = /usr/include/efi/x86_64

EFI_CRT = $(shell dpkg -L gnu-efi | grep '/crt0-efi-x86_64.o$$' | head -n 1)
EFI_LDS = $(shell dpkg -L gnu-efi | grep '/elf_x86_64_efi.lds$$' | head -n 1)
EFI_LIBDIR = $(shell dirname "$$(dpkg -L gnu-efi | grep '/libefi.a$$' | head -n 1)")

CFLAGS = -I$(EFI_INC) -I$(EFI_ARCH_INC) -fpic -ffreestanding -fno-stack-protector -fno-stack-check -fshort-wchar -mno-red-zone -maccumulate-outgoing-args

.PHONY: all clean check

all: check BOOTX64.EFI

check:
\t@test -f "$(EFI_CRT)" || (echo "ERROR: GNU-EFI startup object not found."; exit 1)
\t@test -f "$(EFI_LDS)" || (echo "ERROR: GNU-EFI linker script not found."; exit 1)
\t@test -f "$(EFI_LIBDIR)/libefi.a" || (echo "ERROR: libefi.a not found."; exit 1)
\t@test -f "$(EFI_LIBDIR)/libgnuefi.a" || (echo "ERROR: libgnuefi.a not found."; exit 1)
\t@test -f main.c || (echo "ERROR: main.c is missing."; exit 1)

main.o: main.c
\t$(CC) $(CFLAGS) -c main.c -o main.o

boot.so: main.o
\t$(LD) -nostdlib -znocombreloc -T "$(EFI_LDS)" -shared -Bsymbolic "$(EFI_CRT)" main.o -L"$(EFI_LIBDIR)" -lefi -lgnuefi -o boot.so

BOOTX64.EFI: boot.so
\t$(OBJCOPY) -j .text -j .sdata -j .data -j .dynamic -j .dynsym -j .rel -j .rela -j .reloc --target=efi-app-x86_64 boot.so BOOTX64.EFI

clean:
\trm -f main.o boot.so BOOTX64.EFI
"""

Path("Makefile").write_text(content, encoding="utf-8")
print("Makefile created with real TAB characters.")
PY

The Python command writes the Makefile into the current directory and inserts literal TAB characters for every command recipe. You do not need to type any TABs yourself.

Step 5 — Verify and build

First verify that both files exist:

cd ~/osforge-bootlab/uefi
ls -la

You should see main.c and Makefile. Check that Make can read the build rules:

make -n

Then build:

make clean
make

If successful, verify the output:

ls -l BOOTX64.EFI
file BOOTX64.EFI
Expected result: a file named BOOTX64.EFI. If the build reports a missing GNU-EFI file or another linker error, use the troubleshooting section below.

Step 6 — Create a FAT disk image

Run these commands from the UEFI project directory after the build succeeds:

mkdir -p esp/EFI/BOOT
cp BOOTX64.EFI esp/EFI/BOOT/BOOTX64.EFI

dd if=/dev/zero of=uefi.img bs=1M count=64
mkfs.fat -F 32 uefi.img
mcopy -i uefi.img -s esp/EFI ::/

Step 7 — Find UEFI firmware for QEMU

find /usr/share/OVMF /usr/share/ovmf \
  -type f 2>/dev/null

Look for the x86-64 firmware code image, often called OVMF_CODE.fd. Some installations also provide a variable-store template called OVMF_VARS.fd. If present, copy the variable template to your project directory using its actual path:

cp /PATH/TO/OVMF_VARS.fd ./OVMF_VARS.fd

Replace the example path with the path found on your system. Start QEMU with the real firmware paths:

qemu-system-x86_64 
  -machine q35 
  -m 512 
  -drive if=pflash,format=raw,readonly=on,file=/PATH/TO/OVMF_CODE.fd 
  -drive if=pflash,format=raw,file=OVMF_VARS.fd 
  -drive format=raw,file=uefi.img

Replace /PATH/TO/OVMF_CODE.fd with the actual firmware path. If your distribution packages OVMF differently, follow its package documentation. WSL may require a supported graphical display setup to show the QEMU window.

Step 8 — Build toward a real kernel loader

  1. Locate and validate a kernel image.
  2. Load the kernel into suitable memory.
  3. Collect memory-map information and define a documented kernel handoff structure.
  4. Call ExitBootServices correctly before taking over memory management.
  5. Transfer control to the kernel entry point using the agreed calling convention.

The current example only prints a message. It does not yet load a separate OS kernel.

3. Legacy BIOS bootloader tutorial

This lab creates a 512-byte BIOS boot sector using NASM. It prints a message using BIOS video services and then halts.

Step 1 — Create the BIOS project

mkdir -p ~/osforge-bootlab/bios
cd ~/osforge-bootlab/bios

Step 2 — Create boot.asm

cat > boot.asm <<'EOF'
bits 16
org 0x7C00

start:
    xor ax, ax
    mov ds, ax
    mov es, ax
    mov ss, ax
    mov sp, 0x7C00

    mov si, message

print_character:
    lodsb
    test al, al
    jz finished

    mov ah, 0x0E
    int 0x10
    jmp print_character

finished:
    cli

halt:
    hlt
    jmp halt

message db 'OSForge BIOS Bootloader!', 13, 10
        db 'The boot sector is running.', 0

times 510 - ($ - $$) db 0
dw 0xAA55
EOF

Step 3 — Assemble the boot sector

nasm -f bin boot.asm -o boot.bin
wc -c boot.bin

The expected size is exactly 512 bytes.

Step 4 — Test in QEMU

qemu-system-i386 \
  -drive file=boot.bin,format=raw,if=floppy

The virtual machine should display the message and halt. This is a bootable demonstration sector, not a full kernel loader. A full BIOS loader must read additional sectors and prepare the CPU environment required by the kernel.

QEMU or VirtualBox? QEMU is convenient for rapid testing. VirtualBox can also be used, but select firmware that matches the lab: enable EFI for UEFI testing and disable EFI for legacy BIOS testing where supported.

4. Troubleshooting

No targets specified and no makefile found

Make cannot find a Makefile in the current directory. Return to the UEFI project directory and inspect its contents:

cd ~/osforge-bootlab/uefi
pwd
ls -la

If Makefile is missing, repeat Step 4. If it is named Makefile.txt, rename it:

mv Makefile.txt Makefile

No rule to make target 'clean'

Make found a file but it may not contain the correct rules. Recreate the Makefile using the Python command in Step 4, then run:

make clean
make

missing separator (did you mean TAB instead of spaces?)

This means a Makefile recipe line starts with spaces instead of a literal TAB. Do not try to repair the indentation by hand. Repeat Step 4's Python command, which writes the tabs automatically.

No rule to make target 'main.c'

The C source file is missing from the project directory. Recreate it using Step 2, then verify it:

ls -l main.c

GNU-EFI startup object, linker script, or library not found

dpkg -L gnu-efi | grep -E \
'crt0-efi-x86_64.o|elf_x86_64_efi.lds|libefi.a|libgnuefi.a'

If the Makefile's checks fail, the files may be installed in different locations or the package may be incomplete. Use the reported paths to adapt the Makefile for your distribution.

gcc, ld, or nasm not found

sudo apt update
sudo apt install build-essential binutils nasm make gnu-efi python3

objcopy does not support the EFI target

objcopy --info | grep -i efi

If the EFI target is unavailable, the conversion step or binutils installation needs adjustment.

QEMU cannot find the firmware

ls -l uefi.img
find /usr/share/OVMF /usr/share/ovmf -type f 2>/dev/null

Use actual firmware paths from your system rather than the example paths above.

5. Completion checklist

  • Ubuntu, Debian, or WSL has the required tools installed.
  • main.c and Makefile exist in the UEFI directory.
  • The Makefile was generated with real TAB characters.
  • make produces BOOTX64.EFI.
  • The FAT image contains EFI/BOOT/BOOTX64.EFI.
  • The UEFI application is tested with QEMU and OVMF.
  • The BIOS example assembles to exactly 512 bytes.
  • The BIOS example boots in QEMU.
