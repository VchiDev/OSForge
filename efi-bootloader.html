UEFI & BIOS Bootloader Lab

Learn how computers start operating systems. Build a UEFI application, assemble a BIOS boot sector, and test both in a virtual machine.

Overview Setup UEFI Lab UEFI Testing BIOS Lab UEFI: Read Files UEFI: Graphics UEFI: Memory Map BIOS: Disk Loading BIOS: Stage 2 BIOS: Protected Mode Troubleshooting Resources

What you'll build

UEFI application

Compile a 64-bit EFI application named BOOTX64.EFI using GCC and GNU-EFI.

UEFI virtual machine

Place the application on a FAT disk image and run it using QEMU and OVMF firmware.

Legacy BIOS boot sector

Write a 16-bit assembly boot sector, assemble it with NASM, and test it with QEMU.

Important distinction: A UEFI application and a BIOS boot sector are different executable formats. UEFI firmware loads EFI applications from a supported filesystem; legacy BIOS loads a boot sector from a boot device. The two labs use separate workflows.

These labs are educational starting points. A working bootloader does not automatically provide a complete operating system, memory manager, process scheduler, device drivers, or graphical interface.

1. Set up your development environment

These instructions target Ubuntu, Debian, or Ubuntu running through Windows Subsystem for Linux (WSL). The package names and firmware paths can vary by distribution.

Install the development tools

sudo apt update
sudo apt install build-essential binutils gcc make gnu-efi nasm 
  qemu-system-x86 ovmf dosfstools mtools python3

The main tools are:

Tool Purpose
GCC Compiles C source code.
GNU LD Links object files into a shared ELF object for the GNU-EFI workflow.
GNU objcopy Converts the linked ELF object into an EFI-compatible PE/COFF executable.
GNU-EFI Provides EFI headers, startup objects, libraries, and linker scripts.
NASM Assembles the legacy BIOS boot sector.
QEMU Runs a virtual computer for testing.
OVMF Provides UEFI firmware for QEMU.
mtools / dosfstools Creates and populates a FAT disk image without needing a physical disk.

Using Visual Studio Code

  1. Install Visual Studio Code on Windows or Linux.
  2. For WSL, install Microsoft's WSL extension.
  3. Open your project directory in the WSL environment.
  4. Run build commands in the Ubuntu/WSL terminal, not a separate Windows terminal.

Keep the source files in the same environment where the compiler and build tools are installed. For this tutorial, the working directory will be ~/osforge-bootlab.

Shell reminder: The commands in the UEFI and BIOS labs use Bash on Ubuntu or Ubuntu under WSL. Run them in the Ubuntu terminal, not directly in Windows PowerShell or CMD. PowerShell is suitable for launching WSL (for example, with wsl), but Linux commands such as apt, make, and dpkg run inside Ubuntu.

2. UEFI lab: build an EFI application

UEFI applications are commonly stored as PE/COFF files. On x86-64 systems, the standard removable-media boot path is EFI/BOOT/BOOTX64.EFI.

Create the project directory

mkdir -p ~/osforge-bootlab/uefi
cd ~/osforge-bootlab/uefi

Create main.c

This minimal application prints a message and waits for a key. It uses GNU-EFI's UEFI interfaces. 

cat > main.c <<'EOF'
#include <efi.h>
#include <efilib.h>

EFI_STATUS EFIAPI efi_main(
    EFI_HANDLE ImageHandle,
    EFI_SYSTEM_TABLE *SystemTable
) {
    InitializeLib(ImageHandle, SystemTable);

    Print(L"Welcome to the OSForge UEFI Lab!\r\n");
    Print(L"Your EFI application has started successfully.\r\n");
    Print(L"Press any key to exit.\r\n");

    SystemTable->ConIn->Reset(SystemTable->ConIn, FALSE);

    EFI_INPUT_KEY Key;
    while (SystemTable->ConIn->ReadKeyStroke(
        SystemTable->ConIn, &Key
    ) == EFI_NOT_READY) {
        SystemTable->BootServices->Stall(10000);
    }

    return EFI_SUCCESS;
}
EOF

Locate the GNU-EFI build files

GNU-EFI files are not installed at exactly the same paths on every distribution. These commands discover the installed paths. 

dpkg -L gnu-efi | grep 'crt0-efi-x86_64.o'
dpkg -L gnu-efi | grep 'elf_x86_64_efi.lds'
dpkg -L gnu-efi | grep '/libefi.a'

If the commands return no results, check that the gnu-efi package installed successfully.

Create the Makefile safely

Makefiles require actual TAB characters at the beginning of recipe lines. To avoid editor or copy-and-paste whitespace problems, use Python to write the file. 

python3 - <<'PY'
from pathlib import Path

content = r'''CC = gcc
LD = ld
OBJCOPY = objcopy

EFI_INC = /usr/include/efi
EFI_ARCH_INC = /usr/include/efi/x86_64

EFI_CRT = $(shell dpkg -L gnu-efi | grep '/crt0-efi-x86_64.o$$' | head -n 1)
EFI_LDS = $(shell dpkg -L gnu-efi | grep '/elf_x86_64_efi.lds$$' | head -n 1)
EFI_LIBDIR = $(shell dirname "$$(dpkg -L gnu-efi | grep '/libefi.a$$' | head -n 1)")

CFLAGS = -I$(EFI_INC) -I$(EFI_ARCH_INC) -fpic -ffreestanding -fno-stack-protector -fno-stack-check -fshort-wchar -mno-red-zone -maccumulate-outgoing-args

.PHONY: all clean check

all: check BOOTX64.EFI

check:
	@test -f "$(EFI_CRT)" || (echo "ERROR: GNU-EFI startup object not found."; exit 1)
	@test -f "$(EFI_LDS)" || (echo "ERROR: GNU-EFI linker script not found."; exit 1)
	@test -f "$(EFI_LIBDIR)/libefi.a" || (echo "ERROR: libefi.a not found."; exit 1)
	@test -f "$(EFI_LIBDIR)/libgnuefi.a" || (echo "ERROR: libgnuefi.a not found."; exit 1)
	@test -f main.c || (echo "ERROR: main.c is missing."; exit 1)

main.o: main.c
	$(CC) $(CFLAGS) -c main.c -o main.o

boot.so: main.o
	$(LD) -nostdlib -znocombreloc -T "$(EFI_LDS)" -shared -Bsymbolic "$(EFI_CRT)" main.o -L"$(EFI_LIBDIR)" -lefi -lgnuefi -o boot.so

BOOTX64.EFI: boot.so
	$(OBJCOPY) --input-target=elf64-x86-64 --output-target=efi-app-x86_64 -j .text -j .sdata -j .data -j .dynamic -j .dynsym -j .rel -j .rela -j .reloc boot.so BOOTX64.EFI

clean:
	rm -f main.o boot.so BOOTX64.EFI
'''

Path("Makefile").write_text(content, encoding="utf-8", newline="\n")
print("Makefile created with real TAB characters.")
PY

Build the EFI application

make clean
make
Verified build fix: GNU Binutils 2.46

GNU objcopy must read boot.so as an ELF input and write BOOTX64.EFI as an EFI PE/COFF output. Using --target=efi-app-x86_64 can make objcopy try to interpret the input as the EFI format, producing file format not recognized.

The Makefile now explicitly sets both formats: --input-target=elf64-x86-64 for boot.so and --output-target=efi-app-x86_64 for BOOTX64.EFI.

If your distribution uses a different ELF input target name, run objcopy --info and choose the matching x86-64 ELF target listed by your installed Binutils.

Verify the result

file BOOTX64.EFI

For the tested environment, the output was:

BOOTX64.EFI: PE32+ executable for EFI (application), x86-64 (stripped to external PDB), 6 sections

This confirms that the output is recognized as a 64-bit EFI application. It does not yet prove that the firmware can execute it, so continue to the virtual-machine test.

3. Test the UEFI application in QEMU

This lab creates a virtual FAT disk image containing the standard UEFI fallback boot path. It does not require a physical USB drive.

Step A — Find your OVMF firmware

find /usr/share -iname '*OVMF*' 2>/dev/null

Look for a firmware code image, often named something similar to OVMF_CODE.fd or OVMF_CODE_4M.fd. Some distributions provide separate firmware files for writable UEFI variables, such as OVMF_VARS.fd.

Do not assume that every machine uses the same path. The next commands use variables so you can enter the paths that actually exist on your system.

Step B — Create the virtual FAT disk

Run these commands from the UEFI project directory, where BOOTX64.EFI exists. 

cd ~/osforge-bootlab/uefi

truncate -s 64M uefi.img
mkfs.vfat uefi.img

mmd -i uefi.img ::/EFI
mmd -i uefi.img ::/EFI/BOOT

mcopy -i uefi.img BOOTX64.EFI ::/EFI/BOOT/BOOTX64.EFI

mdir -i uefi.img ::/EFI/BOOT

The last command should list BOOTX64.EFI on the virtual FAT filesystem.

Step C — Start QEMU with UEFI firmware

Set OVMF_CODE to the actual firmware-code path discovered earlier. If your firmware uses a matching variables image, set OVMF_VARS_TEMPLATE to its actual path as well. 

# Replace this example path with your real firmware path.
OVMF_CODE="/usr/share/OVMF/OVMF_CODE_4M.fd"

# Check that the chosen file exists.
test -f "$OVMF_CODE" && echo "Firmware code found"

If a matching writable variables template is available, use it to create a private copy for this virtual machine: 

# Replace this example path with the actual variables template.
OVMF_VARS_TEMPLATE="/usr/share/OVMF/OVMF_VARS_4M.fd"

test -f "$OVMF_VARS_TEMPLATE" && 
  cp "$OVMF_VARS_TEMPLATE" ./OVMF_VARS.fd

If your distribution provides different filenames or does not provide a variables template, use the appropriate files from its installed OVMF package. The code and variables images must be compatible with each other.

Step D — Launch the virtual machine

If both files exist and are compatible, launch QEMU with: 

qemu-system-x86_64 \
  -machine q35 
  -m 512 
  -drive if=pflash,format=raw,readonly=on,file="$OVMF_CODE" 
  -drive if=pflash,format=raw,file=./OVMF_VARS.fd 
  -drive format=raw,file=./uefi.img

This command expects the writable variables copy created in the previous step. If you are using a distribution with a different OVMF layout, adjust the firmware options to match its packaging.

Expected result: QEMU starts a virtual computer, UEFI firmware discovers the fallback boot path on the FAT disk, and your EFI application displays the OSForge welcome message. Press a key to exit the application.

If QEMU opens but returns to the firmware menu, confirm that the disk contains EFI/BOOT/BOOTX64.EFI, that the firmware is x86-64 UEFI, and that the EFI application was built successfully.

Optional: Use VirtualBox

You can also create a virtual machine in VirtualBox and enable EFI in its system settings. Attach a disk image or virtual disk that exposes a FAT EFI System Partition containing EFI/BOOT/BOOTX64.EFI. VirtualBox configuration differs by version, so verify the firmware setting and boot media before testing.

On Windows with WSL, QEMU graphical windows require a working GUI environment such as WSLg, or you can run QEMU in a supported Linux desktop environment.

4. BIOS lab: create a boot sector

The BIOS lab is separate from the UEFI lab. It creates a 512-byte boot sector for a legacy BIOS virtual machine.

Create the project directory

mkdir -p ~/osforge-bootlab/bios
cd ~/osforge-bootlab/bios

Create boot.asm

cat > boot.asm <<'EOF'
BITS 16
ORG 0x7C00

start:
    xor ax, ax
    mov ds, ax
    mov es, ax
    mov ss, ax
    mov sp, 0x7C00

    mov si, message

print_char:
    lodsb
    test al, al
    jz halt

    mov ah, 0x0E
    int 0x10
    jmp print_char

halt:
    cli

halt_loop:
    hlt
    jmp halt_loop

message:
    db 'Welcome to the OSForge BIOS Lab!', 0

times 510-($-$$) db 0
dw 0xAA55
EOF

Assemble the boot sector

nasm -f bin boot.asm -o boot.bin
wc -c boot.bin

The file must be exactly 512 bytes. The final two bytes are the BIOS boot signature 55 AA in disk-byte order.

Boot it in QEMU

qemu-system-i386 \
  -drive format=raw,file=boot.bin,if=floppy
Expected result: The QEMU window displays Welcome to the OSForge BIOS Lab! and then halts.

This example uses BIOS video services and is intended for legacy BIOS emulation. It is not a UEFI application and should not be launched through the UEFI instructions above.

UEFI lesson 2: Find and read a file

UEFI applications can use firmware protocols to access files on a filesystem. A typical next step is loading a kernel file from the EFI System Partition. This lesson introduces the sequence; it is not a complete kernel loader.

  1. Get the loaded-image protocol for your own image.
  2. Use its device handle to locate the Simple File System protocol.
  3. Open the volume, then open a known file such as \kernel.elf.
  4. Read the file into allocated memory and check every returned status.

Plan the file-loading routine

/* Pseudocode: protocol and error-handling details omitted. */
image = get_loaded_image_protocol(image_handle);
fs = get_simple_file_system(image->DeviceHandle);
root = fs->OpenVolume(fs);
status = root->Open(root, &kernel_file, L"\kernel.elf", READ_ONLY, 0);
if (EFI_ERROR(status)) {
    Print(L"Could not open kernel.elf\r\n");
    return status;
}
/* Query the file size, allocate a suitable buffer, then read the file. */
Important: This is a protocol-flow example, not drop-in compilable GNU-EFI code. A real loader must use the exact headers and calling conventions from its UEFI library, check file sizes, and validate the kernel format before transferring control.

Checkpoint

Before attempting to execute a kernel, make the application report whether the file opened and how many bytes were read. A successful file read is a useful independent milestone.

UEFI lesson 3: Graphics Output Protocol (GOP)

GOP provides a firmware-selected framebuffer for simple graphics before the operating system installs its own graphics driver. It is not a full GPU API.

Explore the framebuffer

  1. Locate the Graphics Output Protocol.
  2. Inspect the current mode, resolution, pixel format, and scan-line stride.
  3. Draw a small rectangle by writing pixels within the framebuffer bounds.
  4. Keep the framebuffer address, dimensions, stride, and pixel format in a boot-information structure if the kernel will use it later.
/* Conceptual bounds check; adapt pixel layout to the GOP mode. */
if (x < width && y < height) {
    framebuffer[y * pixels_per_scanline + x] = pixel_value;
}

Do not assume that every mode uses the same stride or byte ordering. Use the mode information reported by firmware, and avoid writing beyond the framebuffer allocation.

Checkpoint

Display a solid background or a small color bar, then print the resolution. Once this works, you have a simple visual output path without needing a graphics driver yet.

UEFI lesson 4: Memory map and leaving boot services

UEFI tracks memory regions and their types. Before the kernel takes over, a loader usually obtains the memory map, prepares a boot-information structure, and calls ExitBootServices().

Understand the order

  1. Allocate the kernel image, stack, and boot-information structure.
  2. Get the memory map and retain its map key.
  3. Finish all operations that may allocate or free firmware memory.
  4. Call ExitBootServices(image_handle, map_key).
  5. If the map key is stale, fetch a fresh map and retry according to the UEFI specification.
  6. After success, do not call Boot Services; transfer control using the kernel's documented entry convention.
Do not copy a guessed memory map. The map can change when allocations occur. The loader must handle buffer-size changes and stale map keys, and it must define a clear ABI for the kernel entry point.

Checkpoint

First implement logging of memory-map descriptors while still inside Boot Services. Only attempt ExitBootServices() in a virtual machine after the loader's allocation and retry paths are understood.

BIOS lesson 2: Read another disk sector

A 512-byte boot sector is too small for most real loaders. A common design loads a second stage from additional sectors, then lets that stage perform more complex work.

What the first stage needs to do

  1. Save the BIOS boot drive number from DL before using it.
  2. Prepare a disk address packet or use a supported BIOS disk-read service.
  3. Read a known sector into a safe memory location.
  4. Check the carry flag and handle read failures instead of jumping blindly.
  5. Transfer control only after verifying that the second-stage bytes were loaded.
; NASM concept only — not a complete disk reader
boot_drive: db 0

start:
    mov [boot_drive], dl
    ; Build a BIOS disk-address packet in memory.
    ; Use INT 13h extensions (AH=42h) where supported.
    ; Check CF after INT 13h and display an error if set.
    ; Jump to the second stage only after a successful read.

Real-mode disk access has compatibility details: the drive number must be preserved, the packet must be correctly laid out and aligned, and the target buffer must not cross problematic memory boundaries. Test with a disk image and a known sector first.

Checkpoint

Put a recognizable byte pattern in a later sector of a raw disk image. Have the first stage read it and verify the pattern before attempting to execute a second stage.

BIOS lesson 3: Design a two-stage loader

Separate the tiny boot sector from the larger loader. The first stage should do as little as possible: establish a predictable CPU state, remember the boot drive, load stage two, and report failures.

Suggested memory and control-flow plan

  • Stage 1: loaded by firmware at the conventional boot address; sets up segments and stack, reads stage two, and jumps to it.
  • Stage 2: can include a better console, disk-reading routines, a filesystem reader, and a kernel-loading routine.
  • Kernel handoff: pass a documented boot-information structure and define the CPU mode, stack, and entry address expected by the kernel.

Do not assume the registers, stack, or all segment values have the state you want just because the code worked in one emulator. Initialize the state your code depends on and document the handoff contract.

Checkpoint

Make stage two print a different message from stage one. That confirms the disk read and control transfer worked before adding filesystem or kernel-loading complexity.

BIOS lesson 4: Preparing for protected mode

On x86, a 32-bit protected-mode kernel needs more than a jump instruction. The loader must prepare a Global Descriptor Table (GDT), disable interrupts during the transition, enable the PE bit in CR0, and perform a far jump to reload CS.

Transition checklist

  1. Load a valid GDT with a null descriptor and appropriate code/data descriptors.
  2. Disable maskable interrupts and ensure the boot code has a known stack.
  3. Set the protection-enable bit in CR0.
  4. Use a far jump to a 32-bit code selector and set the data segment registers.
  5. Set a known 32-bit stack and jump to the kernel entry point.
Advanced step: This page deliberately does not provide a blind copy-paste mode switch. Descriptor values, assembler mode, memory addresses, and the kernel's entry convention must agree. Build and test this as a separate milestone in QEMU before combining it with disk loading.

Checkpoint

After the transition, write a short marker to a known text-mode video-memory location or use a carefully prepared serial output path. If the VM resets or hangs, simplify the transition and inspect it with QEMU's debugger.

5. Troubleshooting

make: No rule to make target 'clean'

You are probably in the wrong directory, or your Makefile does not contain a clean: target. Run pwd and ls to check your current directory.

missing separator

Makefile recipe lines must begin with a real TAB, not spaces. The Python-based Makefile creation step above writes the necessary TAB characters.

objcopy: boot.so: file format not recognized

Check the input with file boot.so and inspect the supported output formats with objcopy --info. The input and output formats must be specified separately. Use --input-target=elf64-x86-64 for the ELF linker output and --output-target=efi-app-x86_64 for the EFI file. The provided Makefile now specifies both formats explicitly. If your Binutils lists a different x86-64 ELF target, use the exact matching name shown by objcopy --info.

GNU-EFI startup object not found

Check whether GNU-EFI is installed with dpkg -L gnu-efi. If the required files are installed in a different location, update the Makefile's discovery logic or paths for your distribution.

libefi.a or libgnuefi.a is missing

Use dpkg -L gnu-efi to find the libraries and confirm that both are present. Some distributions place architecture-specific libraries in a separate directory.

EFI_INC or header files are missing

Check for /usr/include/efi/efi.h and /usr/include/efi/x86_64/. If your distribution uses different include paths, adjust EFI_INC, EFI_ARCH_INC, and the compiler options.

BOOTX64.EFI builds but does not boot

  • Confirm that the disk contains EFI/BOOT/BOOTX64.EFI.
  • Use x86-64 UEFI firmware for this x86-64 application.
  • Check that the OVMF code and variables images are compatible.
  • Confirm that the firmware is booting the intended disk image.
  • Rebuild after changing source files, then copy the new executable to the disk image.

QEMU cannot open a graphical window

Run QEMU from a Linux desktop session or a WSL environment with working graphical support. Check that the QEMU system emulator package is installed and that your display environment is available.

BIOS boot sector is not 512 bytes

Ensure that the source includes padding through byte 510 and the signature dw 0xAA55. Reassemble and verify the output with wc -c boot.bin.
